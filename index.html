Ruptiv AtlasView — infrastructure setup and security review

AtlasView uses a proportionate managed-service architecture. The highest-value improvements are deployment trust, runtime identity separation, operational visibility, and verified access enforcement—not a platform rebuild. This review distinguishes observed configuration from untested behavior. It is not a penetration test or a CIS compliance attestation.

Scope and authority

AtlasView production on GCP, low traffic, October 30 launch, approximately 99% availability. Recovery targets remain a single workstream: three hours restoration and less than ten minutes data loss. Retail is excluded unless a direct dependency is established. The infrastructure owner manages infrastructure; changes use Terraform.

Inspection was read-only. No cloud/settings changes, deployments, secret payload access, SQL records, log-content reads, probes or restore exercises were performed. Exact implementation proposals and exercises require separate approval.

Evidence and source

Assessment snapshot: October 1, 2026. Based on live GCP and GitHub configuration reads and a pinned infrastructure source revision. Raw evidence remains outside this public site. Findings distinguish configured controls from tested behavior; source must be refreshed before changes.

Architecture

Deployment trust

This is configuration topology, not proof of functional/authentication behavior. Engine and gateway load-balancer routing still requires route-level verification.

Coverage and findings

1. Governance and identity — PARTIAL; high-priority improvement

Live project IAM grants Owner to two administrators. Terraform apply holds broad infrastructure administration including project IAM, service accounts, secrets, KMS, networking, compute load balancers and Cloud Run. That may be necessary for its current ownership scope, but compromise has project-wide blast radius. Runtime identities are separate from deployment, except embedder reuses engine-rt.

No user-managed keys were found on tf-apply, engine-rt or memory-rt. This is a checked subset, not all identities. Effective iam.disableServiceAccountKeyCreation is not enforced. Human MFA, inherited organization grants, other service-account keys and access-review cadence remain unverified.

Recommend: protect the deploy trust boundary first; evaluate enabling key-creation restrictions after dependency inventory; review broad human privileges and designate explicit break-glass custody. Do not invent a mandatory two-person GCP ceremony.

2. Federation and deployment — VERIFIED CONFIGURATION GAP; high priority

Live provider trusts repository claims for the infrastructure and application repositories. Apply SA accepts the exact environment subject the infrastructure repository’s production environment. However, the prod Environment has no required reviewers or deployment-branch policy. An environment subject is not proof that only main can deploy when GitHub imposes no ref restriction.

Plan SA trusts the infrastructure repository without a branch condition. Its state-bucket role is storage.objectAdmin; calling it read-only is misleading. Object mutation can support Terraform locking but can also modify/delete state. PR workflows execute repository-controlled code with plan identity credentials. Same-repository PR guards exclude forks but do not make internal branch code trusted.

Main rules require one approving review but no CODEOWNER, stale-dismissal, last-push approval or returned required-status-check rule. Bypass actors include administrators and integrations. CODEOWNERS contains an email identifier; verify GitHub's effective owner resolution rather than assuming it resolves to the intended account.

Recommend: enforce the intended production ref at platform/cloud boundaries; bind approval to current changes; constrain integration bypass use; inspect plan-state mutation/secret exposure before adjusting plan access. Avoid removing lock permissions blindly. Preserve a small-team usable approval path.

3. Public access and TLS — CONFIGURATION REVIEWED; behavior unverified

Engine and MCP gateway have public ingress and invokerIamDisabled=true. Production tfvars explicitly set enable_iap=false. No enabled IAP configuration was returned from either backend or service reads. Therefore application auth is the load-bearing boundary; employee IAP allowlist claims are rejected. Verify authentication, authorization and direct run.app access for both client and machine routes. Public ingress alone is not a vulnerability.

HTTPS proxy has a certificate and no custom SSL policy. Both backend reads have request logging enabled and no securityPolicy field. A custom minimum TLS policy is a reasonable proposal once client compatibility is known. Cloud Armor is an optional, costed abuse-control decision, not proof the current service lacks provider DDoS protection. Any edge control must account for direct service URL bypass.

4. Network and administrative access — sound baseline; hardening opportunity

Live Cloud Run uses Direct VPC egress on the custom production subnet. Engine/memory route all traffic; embedder routes private ranges. Cloud NAT exists. A Serverless VPC Access connector is NOT required when Direct VPC egress is used.

A Tailscale gateway VM sits on the custom subnet with no external IP, Debian 12 license, vTPM and integrity monitoring enabled, Secure Boot disabled. OS patching, Tailscale ACLs, operator authentication and key renewal remain unverified. Its cloud-platform OAuth scope is not alone proof of excessive IAM.

Default-network SSH/RDP rules are legacy risks, but the inspected VM and Cloud Run interfaces use the custom VPC. Do not describe them as exposing these workloads. Remove/restrict only after an attachment/owner check. Production subnet flow logs are disabled; enable sampled logs with explicit retention/cost if useful for incident response—not necessarily a BigQuery pipeline.

5. Compute, scaling and service identity — proportionate; tuning unproven

All four live services use digest-addressed images, one warm revision instance and bounded revision scaling. Engine: 2 CPU/1Gi, revision max6, concurrency80. Memory: 1 CPU/512Mi, max3, concurrency80. Embedder: 2 CPU/2Gi, max3, concurrency160. Gateway: 1 CPU/512Mi, max3, concurrency80. Service-level maximums also exist and differ from revision values; do not infer one effective capacity by summing raw settings.

Services have TCP startup probes and 300s request timeouts. A one-attempt/240s startup probe is not automatically an aggressive fault; it needs documented semantics and measured startup. No explicit application-level liveness probe was returned. Port readiness does not establish dependency/workflow health.

Embedder uses engine-rt, which has KMS custody decryption access. This is a concrete least-privilege improvement candidate: separate the model identity if it does not need engine authority. Memory/engine share SQL with max_connections=100 from earlier reads; reconcile actual connection pool limits with aggregate autoscaling before capacity conclusions. Load testing and image/OS vulnerability analysis were not executed.

6. Data, database and storage — good baseline; narrow safeguards needed

Cloud SQL is private, connector-required, zonal, auto-growing storage, IAM auth enabled and PITR enabled. SSL mode allows unencrypted/encrypted connections, but required Cloud SQL Connector must be considered before calling traffic unencrypted. Verify actual consumer connector paths; do not change TLS mode blindly. SQL role grants/RLS and connection-pool behavior were not inspected.

All three discovered buckets have uniform bucket-level access and seven-day soft deletion. State has versioning plus explicit public prevention; build artifacts explicit public prevention; migration bucket inherits public prevention and effective project policy enforces it. The alleged UBLA gap is false.

State bucket retains legacy projectViewer object-reader and projectOwner/projectEditor grants. Review sensitive-state readers; no state bytes were pulled. Migration bucket grants objectAdmin to a Cloud SQL service agent from project number a separate project and objectViewer to the current project service agent. Identify the external project's purpose before retaining/removing that grant. It is a potential cross-project trust issue, not evidence of data theft.

Database API deletion protection and retainBackupsOnDelete remain false. Prepare exact Terraform controls; no replacement/deletion is acceptable remediation.

7. Secrets and cryptography — configuration observed; rotation/access scope partial

Secret Manager holds referenced runtime credentials. Listed secrets have no rotation schedule returned; creation date does not establish last rotation. Rotation workflows/procedures and per-secret IAM need full reconciliation, especially emergency revocation and staged database credential changes.

KMS custody key has scheduled rotation and engine-rt encrypter/decrypter access. Signing key is asymmetric; do not apply symmetric automatic rotation assumptions to signing keys. Key version custody, signing-principal permissions, destruction controls and verifier rollover remain gaps.

8. Logging, monitoring and incident operations — improvement required

Default log bucket retains 30 days; Required bucket is locked with 400 days. Default sinks already route admin/system/access-transparency logs into Required. Claiming all audit logs expire after 30 days is wrong.

Project auditConfigs is empty; inherited Data Access configuration remains unverified. Decide targeted Secret Manager, KMS, state and privileged access logging with cost/privacy considerations. No need to prescribe a separate year-long archive without a threat/retention requirement.

Earlier live Monitoring reads returned no project alert policies, channels or uptime checks. Confirm external coverage; otherwise add actionable user-facing availability, error/latency, SQL connection/storage and security-change alerts with tested delivery and an incident owner. VPC flow logs are disabled; prioritize actionable alerts over collecting logs nobody reviews.

9. Supply chain and IaC operations — strengths and missing proof

Terraform roots have lockfiles and GCS backends with native locking support. Runtime images are digest-addressed. Actions use version tags (e.g. checkout@v4, auth@v3), not immutable commit SHAs in the inspected workflows. Pin critical actions to reviewed SHAs and maintain updates.

Artifact Registry reports SCANNING_DISABLED because containerscanning API is not enabled. Do not enable a paid scanner without approval; establish whether existing CI security tooling covers the actual deployed digests, or propose a free local/CI scanner with pinned tooling. Digest pinning proves artifact identity, not vulnerability safety or source provenance.

Workflow deployment/rollback code exists; real source-to-build-to-digest-to-runtime lineage, plan confidentiality/approval binding and successful rollback remain unproven. No Terraform plan was executed, so no blanket no-drift verdict.

10. Cost and quota controls — incomplete

Scaling is bounded; warm services, always-allocated CPU behavior from earlier annotations, NAT, SQL and retained artifacts create fixed cost. Billing is enabled. Budget query failed with 403 after CLI timeout, so budget alerts are UNKNOWN, not absent. Compute quota samples are not evidence of Cloud Run/SQL/AI request headroom.

Recommend budget notification review, actual service quota check, model/API spending caps and artifact lifecycle review. Budget alerts are not hard spending stops. Do not estimate dollar savings without billing evidence.

CIS status

The official CIS landing page lists GCP Foundation v5.0.0. Actual authoritative benchmark PDF/control text has not been established in this review. The worker's numbered mapping is rejected: no proven PDF acquisition, unsupported IDs and MFA incorrectly marked non-applicable. Human MFA remains relevant even when it is not Terraform-managed.

This document is an evidence-backed infrastructure best-practices assessment, not a completed CIS control matrix. Obtain the appropriate authorized benchmark copy, pin its version, then map actual controls to these resource-specific checks. Record manual, inherited, not-applicable and blocked items; do not invent a coverage score. CIS Foundation does not alone cover application auth, managed-service workload configuration, source supply chain or operations.

Decisions and remaining evidence

  • Identify intended enterprise customer URL and auth flow; traces can proceed without waiting for an RTO interview.
  • Confirm production ref/approval policy and legitimate integration bypass purposes.
  • Identify migration service-agent project a separate project.
  • Provide/authorize the actual CIS v5 benchmark copy and verify licensing for the intended use.
  • Confirm alert destination, external monitoring, human MFA enforcement, and billing-budget visibility.
  • Application-source authentication analysis, all-SA keys/inherited org controls, complete secret IAM, VM patch status, vulnerability evidence, Cloud Run/SQL quota headroom, functional auth/load/rollback and restore exercises remain explicit gaps.

Recommendation

Keep the managed architecture. Prioritize the identity/deployment trust chain, app enforcement, useful alerts, runtime least privilege and protected state/data. Do not buy enterprise complexity merely to satisfy a checklist.
